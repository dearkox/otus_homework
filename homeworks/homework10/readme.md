# Домашнее задание №10: Обработчик изменений в элементе инфоблока

### Цель:
обработка событий добавления/изменения/удаления элементов;
отслеживание изменений сущностей CRM.
### Описание/Пошаговая инструкция выполнения домашнего задания:
Написать обработчики событий создания/изменения/удаления:
- элементов инфоблока, которые будут записывать изменения, внесенные пользователем, в сделку;
- сделок, которые будут реагировать на изменения и обновлять элементы инфоблока.

### Пошаговая инструкция:
- Создайте новый инфоблок «Заявки»;
- В нем добавьте поля Сделка, Сумма, Ответственный;
- Добавьте обработчики событий, которые будут отслеживать изменения в Заявках (элементах ИБ) и обновлять сумму и ответственного в Сделках, если они изменились;
- Добавьте обработчики событий, которые будут отслеживать изменения в Сделках и обновлять поля в Заявках, если они изменились.

# Решение

### Основная логика работы:

**При создании заявки:**
- Название формируется автоматически как `Заявка №{ID}` через обработчик `onBeforeAdd` (временное значение) и `onAdd` (финальное)
- Проверяется уникальность сделки: если на выбранную сделку уже есть заявка — выводится ошибка
- Сумма и ответственный из заявки переносятся в привязанную сделку

**При обновлении заявки:**
- Название приводится к формату `Заявка №{ID}` (на случай, если пользователь его изменил)
- Проверяется уникальность сделки
- Сумма и ответственный обновляются в сделке

**При обновлении сделки:**
- Ищется заявка, привязанная к этой сделке
- Сумма и ответственный из сделки переносятся в заявку

### Проблемы и их решение
- Главная проблема — перекрёстная рекурсия. Обновление заявки триггерит обновление сделки, которое снова триггерит обновление заявки.   
Решил через статический флаг `$disableSync` в обоих классах — блокируем ответный обработчик на время синхронизации.   
- Вторая проблема — свойства инфоблока не видны через `ORM`. `ElementTable::getList` работает только с полями инфоблока, но не со свойствами. Использую `CIBlockElement::GetProperty` для чтения и `CIBlockElement::SetPropertyValuesEx` для записи.
- Третья проблема — событие `OnCrmDealUpdate` ненадёжно и возвращает только изменённые поля. Перешёл на D7-событие `onAfterCrmDealUpdate`. Но в нём ключи приходят в `CamelCase (opportunity, assignedById)`, а в старом событии — в `UPPER_CASE (OPPORTUNITY, ASSIGNED_BY_ID)`. Решил через `array_change_key_case($arFields, CASE_UPPER)` — приводим все ключи к единому формату.
- Четвёртая проблема — свойство `DEAL` хранит `ID` сделки с префиксом `D_` (например, `D_123`). Очищаю через `str_replace('D_', '', $value)`.
- Пятая проблема — поле Название в инфоблоке обязательно для заполнения, а пользователь может ввести что угодно, что создаёт путаницу при поиске. Решили формировать название автоматически в обработчике `onBeforeAdd` — устанавливаем временное значение Заявка, а после получения `ID` элемента в `onAdd` обновляем на `Заявка №{ID}`. Это обеспечивает единообразие и упрощает поиск заявок в системе.
Для обновления сделки использую фабрику `Container::getInstance()->getFactory(\CCrmOwnerType::Deal)` с методами `setOpportunity()` и `setAssignedById()`. Название заявки автоматически формируется как `Заявка №{ID}`. Все сообщения об ошибках вынесены в языковые файлы.

В итоге синхронизация работает в обе стороны: при изменении заявки обновляется сделка, при изменении сделки — заявка. Рекурсия исключена.
